# RFC 7591 — OAuth 2.0 Dynamic Client Registration

- Status: Proposed Standard · https://www.rfc-editor.org/rfc/rfc7591 · Conf: OPT

## Назначение
Программная регистрация OAuth-клиентов: `POST /oauth2/register` → `client_id`,
`client_secret` (для confidential) и `registration_access_token`.

## Где в API
- `POST /oauth2/register`
- `registration_endpoint` в discovery-документе
- §32 admin apps — альтернативный путь создания того же клиента

## Conformance
- Регистрация **не открытая**. IAM мультитенантный: открытый endpoint позволил бы
  создавать клиентов в чужом проекте. Initial access token — это project-admin
  токен, и он же определяет проект, в который попадёт клиент.
- `redirect_uris` обязателен; каждый URI должен быть абсолютным HTTP(S).
  Относительный отклоняется, а не нормализуется.
- `token_endpoint_auth_method: none` → public-клиент, секрет не выдаётся (его
  роль выполняет PKCE). Любой другой метод → confidential, секрет выдаётся один
  раз в ответе.
- `application_type: native` → тип клиента `native`; иначе `web`/`spa` по методу
  аутентификации.
- Значение по умолчанию для `token_endpoint_auth_method` — `client_secret_basic`.

## Gotchas
- `client_secret` и `registration_access_token` возвращаются ровно один раз: в
  хранилище лежат только их дайджесты. Повторный `GET` секрет не отдаёт.
- Клиент, созданный через admin API, управляется через admin API: у него нет
  registration access token, и endpoints RFC 7592 его не видят.
- Desired-state apply (`PUT /v1/projects/{id}/admin/clients`) переносит
  registration token hash из текущего состояния: документ описывает конфигурацию,
  а не выданные учётные данные. Иначе прогон IaC молча отзывал бы у клиента
  возможность управлять собой.
- В админ-консоли такой клиент помечен `self-registered`, чтобы правки в UI не
  выглядели последним словом — клиент может их перезаписать.
